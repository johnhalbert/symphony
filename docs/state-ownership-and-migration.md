# State Ownership and Migration Compatibility

This guide explains how the Postgres schema in `db/migrations/postgres/0001_symphony_owned_state.sql` maps to Symphony-owned state, external authorities, and the current file-backed transition period. Use it before adding a persistence repository, reducer, importer, or status projection so new code writes the right state to the right place.

## Ownership decision rules

1. **Canonical Symphony state** is state Symphony must replay to make orchestration decisions: run terminal status, review-loop phase and counters, writeback/approval operation state, idempotency keys, normalized transcript/activity events, and sync cursors.
2. **External snapshots** copy data from another authority to make local reads and correlations durable. Snapshots must keep source timestamps or result evidence when available and must not become the source of truth for the external system.
3. **Projection/read-model state** exists only to serve status APIs and frontend clients. Projection rows are rebuildable from canonical Symphony state plus fresh or timestamped external snapshots.
4. **Raw artifacts** that are large, sensitive, or byte-for-byte retained stay out of projection JSON. Store them in controlled file/object storage and record only bounded metadata and references in Postgres.
5. **Startup and migration paths must be idempotent.** Importing, dual-writing, or rebuilding projections must not transition Linear, push to GitHub, mutate git worktrees, start harness sessions, or burn review/incomplete-turn counters unless the normal orchestrator path explicitly processes that side effect.

## Table ownership map

| Table | Classification | Symphony-owned canonical fields | Snapshot/projection boundary |
| --- | --- | --- | --- |
| `symphony.workspace` | Canonical local routing record plus worktree snapshot | `workspace_key`, issue correlation keys, source kind, configured workspace path, repo/base/branch hints, timestamps | Git and the filesystem remain authoritative for repository contents, checked-out commits, and whether a path still exists. Treat persisted branch/path data as routing hints that must be verified before use. |
| `symphony.issue` | Mixed: canonical lifecycle state plus Linear snapshots | `phase`, `blocked_reason`, review/incomplete/planning counters, `last_*` correlation pointers, summary pointers/references, handoff, merge gate/conflict/merge metadata | Linear remains authoritative for title, description, priority, labels, blockers, lifecycle state names, URLs, and tracker timestamps. `tracker_*`, `*_snapshot`, and `tracker_state_classification` are read snapshots. |
| `symphony.run_session` | Canonical Symphony run/session record | Run id, role, phase/kind, attempt/turn, prompt preview/counts, status as reconciled by Symphony, token counts, cancellation outcome, provider-limit signal, pending approval pointer, failure diagnostics, and workspace/run correlations | Runtime harnesses and external agent sessions remain authoritative for live execution while running. GitHub remains authoritative for PR/check/merge data copied into `pr_*`, `ci_status`, and `last_pushed_at`. |
| `symphony.run_activity_event` | Canonical normalized activity/transcript event log | Ordered event sequence, source, event type, public preview, normalized/redacted payload metadata, raw payload reference | Raw harness/tool payloads are not canonical inline JSON. Use `raw_payload_ref_id` for bulky or byte-for-byte retained payloads. |
| `symphony.chat_message` | Canonical normalized chat/orchestrator message stream | Thread key, issue/run/session correlation, ordered message index, speaker/kind, public preview, sanitized payload metadata | Frontend chat projections are derived from this table; raw tool output or full message bodies that exceed caps use `raw_payload_ref_id`. |
| `symphony.writeback_operation` | Canonical durable outbox | Idempotency key, operation kind, issue/run correlation, status, attempt, next retry time, payload hash, payload, and dead-letter/retry state | Linear and GitHub are authoritative for the external write results. `result_*` fields are evidence snapshots from service-owned processing, not permission to assume the external side effect succeeded without that evidence. |
| `symphony.approval_request` | Canonical operator approval gate | Request id, dedupe key, status, action, evidence cursor, timeout/resolution fields, issue/run correlation | Git/GitHub side effects occur only after an approved request is processed by Symphony. A pending row is not a pushed branch or PR. |
| `symphony.external_sync_cursor` | Canonical polling/import cursor | Source system, cursor key/value, high-water mark, lease, sync timing, and last error | Cursors describe what Symphony has observed, not the contents of Linear, GitHub, git, or a harness. A stale cursor must trigger refresh/rebuild rather than become a data authority. |
| `symphony.raw_payload_reference` | Owned metadata for externally stored artifacts | Owner table/key, storage URI, digest, byte length, media type, compression, redaction status, and metadata | The controlled file/object store owns the raw bytes. Do not put credentials in `storage_uri`, and do not serve referenced bytes through projection payloads without the same redaction policy used for transcripts. |
| `symphony.projection_revision` | Durable projection metadata/read index | Projection name/scope/revision, source revisions/cursors, content digest, generated/expires/superseded timestamps | Revisions identify and validate read models. They may contain Linear/GitHub/git snapshots and Symphony summaries, but stale/missing projection rows should be regenerated or bypassed rather than treated as canonical state. |

## External authority boundaries

- **Linear** owns tracker issues, title/description, priority, labels, blockers, lifecycle state names, comments, and transitions. Symphony stores issue snapshots, local lifecycle counters, and writeback operations that request Linear side effects.
- **GitHub** owns pull requests, reviews, check runs, mergeability, branch protection responses, and merge outcomes. Symphony stores PR metadata snapshots, approval/writeback gate state, and merge evidence produced by service-owned processing.
- **Git worktrees and repositories** own file contents, local branches, commits, merge conflicts, and filesystem state. Symphony stores workspace routing hints and run metadata, then verifies the live worktree before using it.
- **Runtime harnesses and external agent sessions** own live execution, streaming status, and raw session streams while a run is active. Symphony persists normalized run/session metadata, reconciled terminal status, cancellation outcomes, and bounded activity events.
- **Large raw artifacts** are retained outside projection JSON. `raw_payload_reference` rows make the retention auditable with digest/size/redaction metadata while keeping status projections sanitized and bounded.
- **Credentials and operator authorization** remain in runtime configuration, environment, or external secret stores. Postgres may persist approval decisions and capability/status snapshots, but not raw secrets.

## Startup and recovery compatibility matrix

| Scenario | Current runtime behavior | Required behavior for a future Postgres-backed mode | Safety invariant |
| --- | --- | --- | --- |
| Postgres absent | There is no database configuration switch in `0001`; the CLI constructs `FileRunTranscriptStore`, `FileIssueLifecycleStore`, `FileWritebackOutboxStore`, and `FileOperatorApprovalStore` under `workspace.stateDir`. | Continue to start on the existing file-backed stores unless a later explicit DB mode is configured. Missing Postgres must not make the current file-backed workflow unavailable. | Absence of Postgres must not change Linear/GitHub/git/harness state and must not mark a run or issue terminal. |
| Postgres present but empty | The current runtime ignores the database and uses file-backed JSON/JSONL state. | Treat the DB as a cold store. Import or dual-write existing file-backed records with stable keys, fetch fresh external snapshots as needed, and rebuild projections from canonical sources. | Empty tables are not evidence that issues, runs, approvals, writeback operations, or blockers do not exist elsewhere. Do not delete file state or reset counters. |
| Postgres present with stale projections | Current in-process web projections are rebuilt from live/file-backed sources and short-lived cache metadata; persisted projection rows are not read yet. | Compare `projection_revision.source_revisions`, `source_cursors`, `generated_at`, `expires_at`, `superseded_at`, and payload digests with current canonical state. Rebuild or serve a fresh fallback when rows are stale. | Stale projections may affect UI freshness only. They must not drive dispatch, review, approval, writeback, or merge-gate decisions. |
| Projection rows exist without matching canonical rows | Not applicable until a DB reader exists. | Treat the projection as partial UI/cache data. Re-import canonical file-backed state or query external authorities; if canonical rows are unavailable, return partial status rather than reconstructing lifecycle or outbox state from projection payloads. | Projection payloads are not a recovery source for writeback status, approval state, review counters, or run terminal status. |
| Existing file-backed state is newer than Postgres | File-backed state is the active source during the transition. | The active configured store wins. Importers should compare timestamps/revisions and upsert newer file records without overwriting them with stale DB rows. | No migration step may roll back accepted completion reports, review verdicts, approval decisions, writeback attempts, or terminal run records. |
| Interrupted import or dual-write replay | File stores already use stable run ids, issue keys, request ids, and idempotency keys. | Use upserts keyed by `run_id`, `(run_id, sequence)`, `issue_key`, approval `request_id`/`dedupe_key`, and writeback `idempotency_key`. Emit/supersede projection revisions only after source writes are durable. | Replays must not duplicate transcript events, recreate approvals, enqueue duplicate external side effects, or burn incomplete-turn/review counters. |
| External authority is unavailable at startup | Existing status APIs can return durable partial data or tracker-unavailable responses depending on endpoint requirements. | Load canonical Symphony state first, mark tracker/GitHub snapshots stale or unavailable, and defer external refresh until credentials/connectivity are valid. | Unset, empty, invalid, or expired credentials should block refresh/writeback paths, not erase snapshots or fabricate external success. |
| Large raw artifact encountered during migration | Existing public transcript projection redacts and caps payloads before serving. | Store bytes in controlled storage, write a `raw_payload_reference` row with digest/size/redaction metadata, and keep projection payloads to previews, counts, and references. | Raw harness output, secrets, and unbounded diagnostics must not be blindly embedded into JSONB projections. |

## File-backed transition constraints

- `0001_symphony_owned_state.sql` is additive schema work. It does not enable a database runtime mode and does not replace the current file-backed stores.
- Existing stores under `workspace.stateDir` remain compatibility contracts: `FileRunTranscriptStore`, `FileIssueLifecycleStore`, `FileWritebackOutboxStore`, `FileOperatorApprovalStore`, and related projection revision notifications must keep their observable API behavior until a later repository layer explicitly migrates them.
- A future persistence implementation should introduce repository interfaces or adapters first, then dual-write/import, then switch reads behind configuration after replay and recovery tests pass.
- Importers must be side-effect free. They may write Postgres rows and projection revisions; they must not post Linear comments, transition Linear issues, push branches, create/update PRs, merge PRs, start harness sessions, or cancel runs.
- Writeback and approval rows must remain idempotent across process restarts. `writeback_operation.idempotency_key` and `approval_request.dedupe_key` are the replay boundaries for publication and tracker writes.
- Projection rebuilds must be monotonic: create a new `projection_revision`, write the projection payload tied to that revision, and only then supersede or stop serving the old revision. If rebuild is interrupted, readers should prefer the newest non-superseded complete revision or fall back to canonical sources.
- Sanitization rules for transcript/status APIs apply before persistence into projection payloads. Store full raw payloads only through `raw_payload_reference` after redaction policy has been applied or explicitly marked.

## Migration phases

1. **Schema available:** apply `0001` where desired, but keep file-backed stores active. This is the current state.
2. **Side-effect-free import:** populate Postgres from file-backed stores and external snapshots using idempotent upserts. Validate counts, digests, and sample records against files.
3. **Dual-write:** write file and Postgres records in the same logical operation, preserving existing projection notification semantics and treating Postgres failures according to an explicit operator policy.
4. **Read cutover:** enable Postgres reads behind a config flag only after startup cases above pass, including absent DB fallback, empty DB cold start, stale projection rebuild, interrupted replay, and invalid credential behavior.
5. **File retirement:** remove file-backed writes only after operators have rollback/export tooling and proof that Linear/GitHub/git/harness authorities are still modeled only as external snapshots or side-effect results.
