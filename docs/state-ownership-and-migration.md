# State Ownership and Migration Compatibility

This guide explains how the configured Postgres migration path in `migrations/postgres` maps to Symphony-owned state, external authorities, and the current file-backed transition period. Use it before adding a persistence repository, reducer, importer, or status projection so new code writes the right state to the right place.

The active migration runner surface is `migrations/postgres/0001_migration_foundation.sql`, the published checksum-stable `migrations/postgres/0002_symphony_owned_state.sql`, `migrations/postgres/0003_projection_freshness_indexes.sql`, `migrations/postgres/0004_run_activity_canonical_channels.sql`, `migrations/postgres/0005_projection_source_freshness.sql`, `migrations/postgres/0006_projection_build_modes.sql`, and `migrations/postgres/0007_project_context_attribution.sql`. The older `db/migrations/postgres/0001_symphony_owned_state.sql` file is the original schema copy, not the service-configured migration runner path; do not implement repositories or reducers from that legacy copy alone.

## Active schema surface

- `migrations/postgres/0001_migration_foundation.sql` establishes the migration runner ledger and must remain first in configured migration order.
- `migrations/postgres/0002_symphony_owned_state.sql` creates the Symphony-owned operational tables, raw payload references, and durable projection/read-model tables. It is published and checksum-stable, so follow-up schema changes must not rewrite it after release.
- `migrations/postgres/0003_projection_freshness_indexes.sql` adds projection `updated_at` freshness columns and recreates projection read indexes with `updated_at DESC` ordering so databases that already applied `0002` can upgrade without migration-checksum conflicts.
- `migrations/postgres/0004_run_activity_canonical_channels.sql` migrates legacy `message` and `status` run activity channel aliases to canonical `chat` and `diagnostic` values, then enforces those canonical run activity channel names for persisted rows.
- `migrations/postgres/0005_projection_source_freshness.sql` adds `projection_revision.source_freshness`, backfills rows that already embedded freshness under `source_cursors.sourceFreshness` / `source_cursors.freshness`, and indexes the JSONB metadata for status/projection readers.
- `migrations/postgres/0006_projection_build_modes.sql` adds `projection_revision.build_mode`, backfills first-scope rows to `bootstrap`, constrains the build-mode vocabulary, and indexes rebuild/bootstrap/incremental revisions for rebuild reports and projection readers.
- `migrations/postgres/0007_project_context_attribution.sql` adds project context attribution columns plus legacy/default backfills across owned operational and projection tables, then re-scopes primary keys, unique constraints, foreign keys, and read indexes by `project_context_id`.
- `migrations/postgres/README.md` is the schema entry point engineers should read first. It links here for state ownership and migration compatibility guidance.

## Ownership decision rules

1. **Canonical Symphony state** is state Symphony must replay to make orchestration decisions: run terminal status, review-loop phase and counters, writeback/approval operation state, idempotency keys, normalized transcript/activity events, chat message reconstruction records, and sync cursors.
2. **External snapshots** copy data from another authority to make local reads and correlations durable. Snapshots must keep source timestamps or result evidence when available and must not become the source of truth for the external system.
3. **Projection/read-model state** exists only to serve status APIs and frontend clients. Projection rows are rebuildable from canonical Symphony state plus fresh or timestamped external snapshots.
4. **Raw artifacts** that are large, sensitive, or byte-for-byte retained stay out of projection JSON. Store them in controlled file/object storage and record only bounded metadata and references in Postgres.
5. **Startup and migration paths must be idempotent.** Importing, dual-writing, or rebuilding projections must not transition Linear, push to GitHub, mutate git worktrees, start harness sessions, or burn review/incomplete-turn counters unless the normal orchestrator path explicitly processes that side effect.

## External authority boundaries

- **Linear** owns tracker issues, title/description, priority, labels, blockers, lifecycle state names, comments, and transitions. Symphony stores issue snapshots, local lifecycle counters, and writeback operations that request Linear side effects.
- **GitHub** owns pull requests, reviews, check runs, mergeability, branch protection responses, and merge outcomes. Symphony stores PR metadata snapshots, approval/writeback gate state, and merge evidence produced by service-owned processing.
- **Git worktrees and repositories** own file contents, local branches, commits, merge conflicts, and filesystem state. Symphony stores workspace routing hints and run metadata, then verifies the live worktree before using it.
- **Runtime harnesses and external agent sessions** own live execution, streaming status, and raw session streams while a run is active. Symphony persists normalized run/session metadata, reconciled terminal status, cancellation outcomes, and bounded activity events.
- **Large raw artifacts** are retained outside projection JSON. `raw_payload_reference` rows make the retention auditable with digest/size/redaction metadata while keeping status projections sanitized and bounded.
- **Credentials and operator authorization** remain in runtime configuration, environment, or external secret stores. Postgres may persist approval decisions and capability/status snapshots, but not raw secrets.

## Startup and recovery compatibility matrix

| Scenario | Current runtime behavior | Required behavior for a future Postgres-backed mode | Safety invariant |
| --- | --- | --- | --- |
| Postgres absent | The database URL is optional. Normal worker/orchestrator startup continues on `FileRunTranscriptStore`, `FileIssueLifecycleStore`, `FileWritebackOutboxStore`, and `FileOperatorApprovalStore`; configured migrations are validated/applied only by explicit migration commands. | Continue to start on the existing file-backed stores unless a later explicit DB mode is configured. Missing Postgres must not make the current file-backed workflow unavailable. | Absence of Postgres must not change Linear/GitHub/git/harness state and must not mark a run or issue terminal. |
| Postgres present but empty | Existing lifecycle/writeback/approval stores still rely on file-backed JSON/JSONL state during the transition. | Treat the DB as a cold store. Import or dual-write existing file-backed records with stable keys, fetch fresh external snapshots as needed, and rebuild projections from canonical sources. | Empty tables are not evidence that issues, runs, approvals, writeback operations, or blockers do not exist elsewhere. Do not delete file state or reset counters. |
| Postgres present with stale projections | Current status/web projections may be rebuilt from live/file-backed sources and projection revision notifications; persisted projection rows are not authoritative lifecycle state. | Compare `projection_revision.source_revisions`, `source_cursors`, `source_freshness`, `generated_at`, `updated_at`, `expires_at`, `superseded_at`, and payload digests with current canonical state. Rebuild or serve a fresh fallback when rows are stale. | Stale projections may affect UI freshness only. They must not drive dispatch, review, approval, writeback, or merge-gate decisions. |
| Projection rows exist without matching canonical rows | Not applicable until a DB reader exists. | Treat the projection as partial UI/cache data. Re-import canonical file-backed state or query external authorities; if canonical rows are unavailable, return partial status rather than reconstructing lifecycle or outbox state from projection payloads. | Projection payloads are not a recovery source for writeback status, approval state, review counters, or run terminal status. |
| Existing file-backed state is newer than Postgres | File-backed state is the active source during the transition. | The active configured store wins. Importers should compare timestamps/revisions and upsert newer file records without overwriting them with stale DB rows. | No migration step may roll back accepted completion reports, review verdicts, approval decisions, writeback attempts, or terminal run records. |
| Interrupted import or dual-write replay | File stores already use stable run ids, issue keys, request ids, and idempotency keys; current schema adds stable event/message ids and run-session scoped sequence constraints. | Use upserts keyed by `run_id`, `(run_session_id, sequence)`, `event_id`, `(run_session_id, external_event_id)`, `message_id`, `(thread_key, message_index)`, `issue_key`, approval `request_id`/`dedupe_key`, and writeback `idempotency_key`. Emit/supersede projection revisions only after source writes are durable. | Replays must not duplicate transcript events, chat messages, approvals, or external side effects, and must not burn incomplete-turn/review counters. |
| External authority is unavailable at startup | Existing status APIs can return durable partial data or tracker-unavailable responses depending on endpoint requirements. | Load canonical Symphony state first, mark tracker/GitHub snapshots stale or unavailable, and defer external refresh until credentials/connectivity are valid. | Unset, empty, invalid, or expired credentials should block refresh/writeback paths, not erase snapshots or fabricate external success. |
| Large raw artifact encountered during migration | Existing public transcript projection redacts and caps payloads before serving. | Store bytes in controlled storage, write a `raw_payload_reference` row with digest/size/redaction metadata, and keep projection payloads to previews, counts, and references. | Raw harness output, secrets, and unbounded diagnostics must not be blindly embedded into JSONB projections. |

## File-backed transition constraints

- The configured `migrations/postgres` schema is additive. `0002_symphony_owned_state.sql`, `0003_projection_freshness_indexes.sql`, `0004_run_activity_canonical_channels.sql`, `0005_projection_source_freshness.sql`, `0006_projection_build_modes.sql`, and `0007_project_context_attribution.sql` do not, by themselves, switch lifecycle, writeback, approval, or transcript reads away from the current file-backed stores.
- The legacy `db/migrations/postgres/0001_symphony_owned_state.sql` copy remains documentation/history for the original schema proposal. The service-configured runner path is `migrations/postgres`, and repository implementations should validate against that current path.
- Existing stores under `workspace.stateDir` remain compatibility contracts: `FileRunTranscriptStore`, `FileIssueLifecycleStore`, `FileWritebackOutboxStore`, `FileOperatorApprovalStore`, and related projection revision notifications must keep their observable API behavior until a later repository layer explicitly migrates them.
- A future persistence implementation should introduce repository interfaces or adapters first, then dual-write/import, then switch reads behind configuration after replay and recovery tests pass.
- Importers must be side-effect free. They may write Postgres rows and projection revisions; they must not post Linear comments, transition Linear issues, push branches, create/update PRs, merge PRs, start harness sessions, or cancel runs.
- Writeback and approval rows must remain idempotent across process restarts. `writeback_operation.idempotency_key` and `approval_request.dedupe_key` are the replay boundaries for publication and tracker writes.
- Projection rebuilds must be monotonic: create a new `projection_revision` with current `source_freshness` and `build_mode`, write the projection payload tied to that revision, update `updated_at` freshness, and only then supersede or stop serving the old revision. If rebuild is interrupted, readers should prefer the newest non-superseded complete revision or fall back to canonical sources.
- `projection_revision.build_mode` distinguishes the first materialization for a scope (`bootstrap`), on-demand route/read-repair maintenance (`incremental`), and explicit rebuild/backfill writes (`rebuild`). Rebuild requests over an already-current row may be reported as unchanged without creating a new revision; the row keeps the original build mode while the rebuild response still records the requested rebuild attempt.
- Sanitization rules for transcript/status APIs apply before persistence into projection payloads. Store full raw payloads only through `raw_payload_reference` after redaction policy has been applied or explicitly marked.

## Migration phases

1. **Schema available:** validate/apply the configured `migrations/postgres` files where desired, but keep file-backed stores active for the existing worker/reviewer workflow.
2. **Side-effect-free import:** populate Postgres from file-backed stores and external snapshots using idempotent upserts. Validate counts, digests, and sample records against files and current external snapshots.
3. **Dual-write:** write file and Postgres records in the same logical operation, preserving existing projection notification semantics and treating Postgres failures according to an explicit operator policy.
4. **Read cutover:** enable Postgres reads behind a config flag only after startup cases above pass, including absent DB fallback, empty DB cold start, stale projection rebuild, interrupted replay, projection-only rows, and invalid credential behavior.
5. **File retirement:** remove file-backed writes only after operators have rollback/export tooling and proof that Linear/GitHub/git/harness authorities are still modeled only as external snapshots or side-effect results.
